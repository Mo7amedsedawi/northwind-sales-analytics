# Northwind Sales Analytics

> **An end-to-end analytical pipeline built around data quality, feature engineering, dimensional modeling, and interactive Power BI reporting.**

---

## Analytical Architecture

This project is designed as a complete analytical pipeline rather than a collection of isolated queries or dashboard visuals.

The core architecture separates **data preparation**, **analytical modeling**, **validation**, and **visual reporting** into distinct layers:

```text
                         NORTHWIND DATA
                               │
                               ▼
                        Raw Transactional Data
                               │
                               ▼
                        Python / Pandas
                               │
                 ┌─────────────┴─────────────┐
                 │                           │
          Data Wrangling              Feature Engineering
                 │                           │
                 └─────────────┬─────────────┘
                               ▼
                       DATA QUALITY LAYER
                               │
                 ┌─────────────┴─────────────┐
                 │                           │
            Valid Records            Invalid / Anomalous
                 │                           │
                 ▼                           ▼
           Clean Dataset               Investigation
                 │
                 ▼
                    STAR SCHEMA
                 ┌───────┼───────┐
                 ▼       ▼       ▼
             Customer Product Employee
                 \       │       /
                  \      │      /
                   └─ fact_sales ─┘
                         │
                         ▼
                       SQLite
                         │
                         ▼
                      Power BI
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
        DAX          Interactive      Tooltips
                     Visuals
          │              │
          └──────────────┼──────────────┘
                         ▼
                     Dashboard
                         │
                         ▼
                     Excel QA
```

The important design decision is that **Power BI is not responsible for fixing the raw data**.

The analytical dataset is prepared, validated, and structured before it reaches the reporting layer.

# 01 — The Analytical Data Layer

The project intentionally works with a focused analytical subset of the Northwind schema:

| Table           | Analytical Role                       |
| --------------- | ------------------------------------- |
| `Orders`        | Order-level transactional information |
| `Order Details` | Product-level order lines             |
| `Products`      | Product attributes                    |
| `Customers`     | Customer attributes                   |
| `Employees`     | Sales employee attributes             |

Instead of loading the entire source schema into the analytical model, the pipeline isolates the entities required to answer the intended sales and operational questions.

This keeps the model focused and makes the downstream Star Schema easier to reason about.

---

# 02 — Feature Engineering Before BI

A major part of the pipeline happens **before Power BI**.

The transactional data is transformed with Pandas into analytical features that can be reused consistently across SQL, Power BI, and QA validation.

### Core engineered features

| Feature                   | Purpose                                                  |
| ------------------------- | -------------------------------------------------------- |
| `Revenue`                 | Net revenue generated by an order line                   |
| `OrderTotal`              | Total monetary value of an order                         |
| `OrderItemCount`          | Number of distinct products in an order                  |
| `OrderQuantity`           | Total quantity of items within an order                  |
| `DaysToShip`              | Operational shipping duration                            |
| `ShipDelayDays`           | Difference between actual shipping and required shipping |
| `IsLate`                  | Binary indicator for late shipment                       |
| `OrderValueCategory`      | Relative classification of order value                   |
| `CustomerOrderCount`      | Number of orders associated with a customer              |
| `CustomerLifetimeRevenue` | Total revenue generated by a customer                    |

The purpose is not simply to create more columns.

The purpose is to move repeated analytical logic into a controlled transformation layer where it can be **validated, reused, and documented**.

---

# 03 — Data Quality Report

One of the central components of the pipeline is the **Data Quality Report**.

Instead of cleaning the dataset blindly, the pipeline first measures the state of the data.

The quality layer evaluates:

| Quality Check             | What It Detects                            |
| ------------------------- | ------------------------------------------ |
| Missing Customer          | Broken customer references                 |
| Missing Product           | Missing product relationships              |
| Missing Employee          | Missing employee relationships             |
| Non-positive Price        | Invalid monetary values                    |
| Non-positive Quantity     | Invalid order quantities                   |
| Invalid Discount          | Discount values outside the expected range |
| Invalid Shipping Dates    | Shipping dates preceding order dates       |
| Extreme Shipping Duration | Potential operational anomalies            |

This creates a distinction between:

> **Data that is unusual**

and

> **Data that is demonstrably invalid.**

That distinction matters.

### An anomaly is not automatically an error.

A suspicious record should be investigated before being removed.

This prevents the common analytical mistake of treating every unusual value as bad data.

---

# 04 — Invalid Rows → Clean Analytical Dataset

After the quality checks, invalid records are isolated through explicit validation rules.

Conceptually:

```text
Raw Sales Data
      │
      ▼
Validation Rules
      │
 ┌────┴────┐
 ▼         ▼
Valid     Invalid
 │          │
 ▼          ▼
Keep     Investigate
 │
 ▼
sales_clean
```

The cleaning logic checks conditions such as:

```python
invalid_rows = (
    (sales["UnitPrice"] <= 0) |
    (sales["Quantity"] <= 0) |
    (sales["Discount"] < 0) |
    (sales["Discount"] > 1) |
    (sales["ShippedDate"] < sales["OrderDate"])
)

sales_clean = sales.loc[~invalid_rows].copy()
```

This creates a reproducible boundary between the **raw analytical input** and the **validated dataset** used downstream.

---

# 05 — Referential Integrity

The pipeline also validates relationships between transactional tables.

Examples include checking whether:

* every order detail references an existing order;
* every order detail references an existing product;
* customer relationships remain valid;
* employee relationships remain valid.

This is important because a dataset can have valid-looking individual rows while still containing broken relationships.

The quality process therefore operates at two levels:

```text
Row-Level Quality
        +
Relationship-Level Integrity
        ↓
Validated Analytical Dataset
```

# 06 — Star Schema

After transformation and validation, the data is reorganized into a compact analytical Star Schema.

```text
                         dim_customer
                              │
                              │ CustomerID
                              ▼
                         ┌───────────┐
                         │           │
                         │ fact_sales│
                         │           │
                         └───────────┘
                           ▲    ▲
                           │    │
                     ProductID  EmployeeID
                           │    │
                           ▼    ▼
                    dim_product  dim_employee
```

### Analytical model

| Table          | Type      | Role                                      |
| -------------- | --------- | ----------------------------------------- |
| `fact_sales`   | Fact      | Transaction-level analytical measurements |
| `dim_customer` | Dimension | Customer context                          |
| `dim_product`  | Dimension | Product context                           |
| `dim_employee` | Dimension | Employee context                          |

### Fact Grain

The grain of `fact_sales` is explicitly defined as:

> **One row = one product line within one order.**

Therefore:

```text
Order ≠ Fact Row

Order Line = Fact Row
```

This definition is critical because it determines how quantities, revenue, order counts, and aggregations must be interpreted.

---

# 07 — Why the Star Schema Matters

The Star Schema is not merely a visual database diagram.

It creates a clean analytical contract between the data layer and the BI layer.

```text
Dimensions
    │
    │ Filtering / Context
    ▼
Fact Table
    │
    ▼
Measures
    │
    ▼
Visual Analytics
```

This allows Power BI to operate on a structured analytical model instead of directly navigating the original transactional structure.

# 09 — Power BI Semantic Layer

Power BI consumes the Star Schema and establishes the dimensional relationships:

```text
dim_customer  1 ─────── * fact_sales
dim_product   1 ─────── * fact_sales
dim_employee  1 ─────── * fact_sales
```

The model uses dimensional filtering rather than relying on uncontrolled bidirectional relationships.

This keeps the analytical model predictable and reduces ambiguity when measures are evaluated.

# 10 — DAX Measures

The dashboard uses explicit DAX measures rather than relying entirely on implicit aggregations.

### Core measures

```DAX
Total Revenue =
SUM(fact_sales[Revenue])
```

```DAX
Total Orders =
DISTINCTCOUNT(fact_sales[OrderID])
```

```DAX
Total Quantity =
SUM(fact_sales[Quantity])
```

```DAX
Average Order Value =
DIVIDE(
    [Total Revenue],
    [Total Orders]
)
```

```DAX
Average Days to Ship =
AVERAGE(fact_sales[DaysToShip])
```

```DAX
Late Orders =
CALCULATE(
    DISTINCTCOUNT(fact_sales[OrderID]),
    fact_sales[IsLate] = TRUE()
)
```

```DAX
Late Order Percentage =
DIVIDE(
    [Late Orders],
    [Total Orders]
)
```

The separation between **prepared columns** and **DAX measures** is intentional:

```text
Python
→ row-level transformation
→ data quality
→ feature engineering

Power BI / DAX
→ analytical aggregation
→ filter context
→ reporting metrics
```

# 15 — Analytical Insights

The analytical model and dashboard reveal several important patterns.

### Revenue Concentration

A relatively small group of products contributes a large share of total revenue.

This indicates that total sales are not distributed evenly across the product catalog and that product-level aggregation is important when interpreting overall performance.

---

### Customer Revenue Concentration

Some customers generate substantially higher lifetime revenue than others.

The combination of:

```text
CustomerOrderCount
+
CustomerLifetimeRevenue
```

allows customer activity to be analyzed beyond simple order frequency.

A customer placing many orders is not necessarily equivalent to a customer generating high monetary value.

---

### Shipping Delays

Shipping delays are concentrated within specific periods or employees.

The inclusion of:

```text
DaysToShip
ShipDelayDays
IsLate
```

allows the model to move from pure sales analysis into operational analysis.

Instead of asking only:

> How much was sold?

the model can also examine:

> How efficiently were those orders fulfilled?

---

### Order Value Variation

Order value varies significantly across customer segments.

This highlights the importance of analyzing revenue at multiple granularities rather than relying solely on total sales.

The model supports comparisons between:

```text
Customer
      ↓
Orders
      ↓
Order Lines
      ↓
Revenue
```

# 17 — Engineering Principles

The project follows several principles that guided the implementation.

### 1. Validate Before Visualize

A polished dashboard built on unvalidated data is still an unreliable analytical product.

### 2. Separate Transformation from Presentation

Python prepares the analytical data.

Power BI presents and explores it.

### 3. Define the Grain

Every fact table must have a clear grain before aggregation logic is designed.

### 4. Investigate Anomalies

Unusual values should not automatically be deleted.

### 5. Prefer Reproducible Transformations

Transformations are implemented as code rather than manual spreadsheet operations.

### 6. Validate Across Layers

Important results should remain consistent from Python to SQLite to Power BI and independent QA.

## Closing Perspective

The objective of this project was not simply to connect a database to Power BI and create charts.

The more important objective was to construct a **controlled analytical pipeline** in which data passes through explicit stages of transformation, validation, modeling, measurement, visualization, and verification.

The resulting system separates the responsibilities of each technology:

```text
Python
→ Prepare

Quality Layer
→ Validate

SQLite
→ Structure

DAX
→ Measure

Power BI
→ Explore

Excel
→ Verify
```

The dashboard is therefore the **final layer of the analytical process**, not the beginning of it.
